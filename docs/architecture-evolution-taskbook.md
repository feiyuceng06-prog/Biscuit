## 1. 要完成什么

在现有自研 Python 核心上，完善任务状态、工具执行、验证证据、上下文和恢复机制。保留现有 CLI 与 Electron 桌面入口、模型接入和工具能力。

希望最终达到：

1. 知道当前任务要求什么、哪些完成了、哪些没有验证。
2. 知道测试对应的是哪一次代码状态，后续修改后不会沿用过期结论。
3. 工具执行经过统一的参数、权限、隔离、记录和取消流程。
4. 中断、重启或压缩上下文后，能恢复任务事实，并识别结果未知的操作。
5. 能用现有评测比较改动前后行为、成功率和成本。

本次按 A—E 五个阶段实施；F 为后续实验，不属于本次必做项。阶段之间沿用已经确认的方案，常规实现选择自主决定，不必每完成一个阶段再询问是否继续。

## 4. 推荐职责边界

```text
CLI / Electron
    ↓
会话与任务控制：目标、约束、验收、状态、预算
    ↓
Agent Loop ←→ 上下文管理 ←→ 模型适配器
    ↓
工具执行入口：参数 → 授权 → 记录 → 隔离执行 → 结果
    ↓
验证记录、任务快照、诊断事件

只读子 Agent 按需参与，费用和取消归父任务管理。
```

这是职责要求，不是固定文件目录。先确定最小模块边界；优先提取工具执行和验证记录，避免为了分层制造大量转发类。

内部数据建议用标准库 dataclass、enum 或现有一致方式实现。模型看到的输出仍应清楚简短，不必把所有内部元数据都塞进上下文。

## 5. 分阶段任务

### A. 核对现状，建立基线

- [ ] 保存当前 HEAD、工作区差异摘要、版本、解释器和依赖环境，避免输出密钥。
- [ ] 核对本任务书所指能力是否已实现或已修正，已完成部分复用，不重复开发。
- [ ] 运行适用的现有检查，区分产品失败、已有失败和环境受限。
- [ ] 在 `docs/` 建立简短设计记录，写明状态所有权、兼容方式、模块边界、必要取舍和迁移顺序。
- [ ] 建立实施检查表，后续阶段完成时更新结果与证据。

验收：有可复查的基线和设计记录，能解释为什么需要后续每项改动。读取现有 benchmark 结果可以辅助定位，不得冒充本次运行。

### B. 验证记录与失效——第一批实现

- [ ] 基于已有复现、verify 和 hooks，增加机器可读的验证记录。
- [ ] 至少保存：验证 ID、任务 ID、命令、cwd、开始/结束时间、退出码、超时/取消、日志引用、代码状态标识、基线/修改后类别。
- [ ] 验证状态区分：通过、失败、未运行、已过期、环境受阻。
- [ ] 文件修改后让旧验证结论失效，包括编辑工具、Shell、MCP 或外部修改等相关路径。无法准确追踪时，保守失效或在使用结论前重新核验。
- [ ] 不单独用 Git HEAD 表示代码状态；必须考虑未提交及未跟踪文件、验证相关配置和工作目录变化。
- [ ] 对大仓库控制指纹计算开销；记录失效策略及其覆盖边界，不能声称完整掌握动态依赖。
- [ ] 保存并恢复验证记录；恢复时重新检查工作区状态，不能直接沿用旧“通过”。
- [ ] 结束代码任务时，展示验证范围和未验证原因。无自动测试的任务可以结束，但不能宣称已验证。
- [ ] 闲聊、只读问答等无需代码验收的任务保持自然结束。

必要回归：验证通过后再修改、验证期间发生修改、命令失败/超时/取消、原有失败基线、会话恢复后文件变化、状态未知。验证期间版本变化时不得标记为最新状态通过。

验收：验证结论能追到真实执行和对应代码状态；后续改动不会继续显示“当前已通过”。

### C. 统一工具执行入口

- [ ] 从现有 `_gate()`、`_pre_tool()`、串并行执行和 `Toolbox.run()` 提取最小执行器，保留兼容入口。
- [ ] 统一顺序：参数检查 → 授权 → 执行前记录 → 隔离执行 → 结果归一化 → 状态更新。
- [ ] hooks、自动 verify、后台命令和 MCP 的相关执行路径纳入一致的权限与信任规则；避免自动命令形成绕行入口。
- [ ] 收拢工具元信息：schema、作用范围、读写/网络性质、并发类别、重试语义、输出预算。保留现有安全默认值。
- [ ] 元信息是调度依据，不能代替执行隔离。MCP 自报只读不能自动取得信任。
- [ ] 在现有 `ToolResult` 上渐进增加可选机器字段：错误码、退出码、耗时、截断、产物引用、修改路径和来源类别。
- [ ] 保留字符串内容、图片、摘要与详情的现有兼容，不让前端处理内部实现细节。
- [ ] 保持只读并行、混合写入保守串行；没有资源隔离证据时不扩大并行范围。
- [ ] 所有工具调用，包括错误、中断和拒绝，都有且只有一个协议结果与其配对。

必要回归：串并行等价性、拒绝不执行、确认范围、参数错误、副作用不被自动重试、输出截断、图片传递、后台命令、取消及调用结果配对。

验收：相同行为没有因提取而改变；所有适用入口确实复用检查，测试不能只覆盖新增包装函数。

### D. 任务状态与恢复

- [ ] 在 session/progress 基础上增加 `schema_version`、`session_id`、`task_id` 和明确工作区标识。
- [ ] 保存用户原始要求与后续修订引用、目标、约束、验收项、待办、预算消耗和验证引用。
- [ ] 区分运行状态与任务结果：等待用户/中断/预算停止等，不混同于完成/部分完成/无法验证。
- [ ] 任务状态按会话/任务隔离；同工作区多个会话互不覆盖。工作区进度如继续保留，应是明确选定任务的视图。
- [ ] 副作用执行前保存准备状态，完成后保存结果；崩溃窗口中的操作标为“结果未知”。
- [ ] 恢复时先核对当前文件、Git、进程或可查询外部状态；未知操作不能盲目重跑。
- [ ] 调用 ID 仅用于关联。对任意 Shell 和外部写入，不宣称能实现恰好一次执行。
- [ ] 关键持久化失败应显式处理；不得套用诊断日志“失败全部忽略”的语义。
- [ ] 保留旧会话可读；新格式按需迁移或读取适配，不批量重写真实用户历史。
- [ ] 统一父任务总预算、截止时间和取消传播，覆盖 helper、子 Agent、reviewer 与后台任务；安全处理仍需收尾的进程。

必要回归：写前、写后记录前崩溃；重启后状态变化；取消传播；预算累计；损坏快照；旧格式读取；同工作区多会话；恢复不会扩大授权。

验收：可解释地恢复到安全边界，不重复未知副作用，不丢未完成验收项，不跨会话串进度。

### E. 上下文与前端边界整理

- [ ] 上下文分清稳定规则、项目事实、任务状态、近期证据和按需历史。
- [ ] 压缩后用程序核对目标/约束引用、未完成验收项、未配对调用、未知操作及运行中 job。
- [ ] 摘要引用验证记录，不能把助手声称的结果升级为执行事实。
- [ ] 保留缓存意识，不因每轮更新状态而频繁改写稳定前缀；对不同 provider 的行为分别验证。
- [ ] 小步封装 provider 历史访问，保留工具配对、多模态和协议必需内容，不进行有损消息转换。
- [ ] 从关键执行链路开始，让运行层产出结构化事件，CLI/Desktop 分别渲染；保留已有协议兼容。
- [ ] 事件 sink 按运行/会话隔离，避免全局 sink 在并发和嵌套执行中串流。
- [ ] 来源类别经过摘要、子 Agent 和记忆转述后仍保留，不能自动提升为用户指令。
- [ ] 保留现有 Dreaming 来源、指纹和应用前校验；当前纯对话来源不能充当测试通过证据。

必要回归：强制压缩后继续任务、约束保持、切换模型、图片与工具历史、两个会话事件隔离、终端/桌面状态一致、来源标记保留。

验收：压缩和更换前端不改变运行事实；保留已有交互能力；不要求本阶段重写全部 UI。

## 6. 测试与评测要求

### 程序正确性

新增测试针对状态边界和实际执行路径，使用临时目录、临时 Git 仓库、隔离 HOME/XDG 与假 provider。不得触碰真实密钥和历史。

检查命令优先采用当前项目约定。研究时核心回归为：

```sh
.venv/bin/python -m unittest discover -s tests -t .
```

桌面相关改动需在 `desktop/` 运行当前适用的 Node 测试、前端构建和集成冒烟；运行前核对 package scripts。检查 Python 3.10 实际运行兼容性；若解释器不可用，说明缺口，语法解析不能冒充运行时验证。

对进程终止和崩溃采用可控的故障注入，检验副作用与恢复记录；不要只测理想路径。不为纯移动代码补大量镜像实现的测试。

### Agent 能力与成本

扩展已有 `evals`，至少准备以下对照：

| 对照 | 要回答的问题 |
|---|---|
| 原基线 vs 执行器提取 | 结构调整是否保持行为 |
| 原验证 vs 版本关联验证 | 是否减少过期验证与错误完成 |
| 原压缩 vs 任务状态核对 | 长任务续接是否更可靠 |
| 原恢复 vs 新恢复 | 是否减少丢任务、重复操作和人工介入 |

固定模型版本、提示配置、任务、工具、环境和预算。记录成功率、样本量、成本、耗时、人工介入、环境失败和预算停止；辅助模型与失败尝试计入总成本。

开发任务与保留任务分开，多次试验，报告不确定性。最终判题保持独立，避免 Agent 改了测试就能改变评分。不用小样本或未经运行的命令宣称性能提升。

若没有付费评测授权，完成可复现的配置、命令与输出格式，交付时明确“程序回归已验证，真实模型收益尚未验证”；架构阶段可据其各自验收标准完成，但整套能力收益不得标记已验收。
